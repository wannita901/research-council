Phase 4 · Build Specs

Vertical Slice Spec — Ideation → Feasibility

Drafted 2026-06-04 · The one runnable slice we build first · Last planning page before code

One slice, end to end: you give an AI4SE topic; three cross-vendor peers research it independently, propose a research idea + a minimal experiment plan, cross-critique, rebut, and the verifier checks whether each plan actually runs; the panel votes and you confirm. This is exactly the eval anchor from Research Framing, so building it = building the experiment harness.

Scope of the slice

InOut (later)
3-vendor parallel research over Hybrid/OpenAlex retrievalOther lifecycle stages (full experiments, writing)
Propose → cross-critique → rebut (1–2 rounds)Full experiment execution (we only feasibility-smoke-test)
Feasibility verifier (staged — see increments)Web UI (architecture already streams to it)
Anonymized panel vote + human confirmJob-queue runner / parallel debates
Checkpointing + full transcript loggingBaselines B0/B3/B4/B5 wiring (next, reuse same core)
Two build increments

Increment 1 the full debate with a mock verifier (an independent model rates feasibility 0–1 with justification). Cheapest test of "does heterogeneous debate work?" — no sandbox.
Increment 2 swap in the real feasibility verifier: generate a minimal runnable scaffold from the experiment plan, execute it in a sandbox, signal = "did it run & emit the metric?". This is the load-bearing piece for RQ2.

1. Data contracts (this slice)

TopicSpec        { area, question?, constraints?, n_rounds=2, seats{openai,claude,gemini} }
ResearchBrief    { vendor, landscape, gap, rationale, refs[] }          # phase 1, per peer
Candidate        { id, vendor, version, title, gap, hypothesis,
                   method, experiment_plan, refs[] }                    # phase 2 (vendor hidden downstream)
Critique         { critic_vendor, target_id, axis: novelty|soundness|feasibility,
                   severity:1..5, claim, needs_verification:bool, evidence_ref? }   # phase 3
Rebuttal         { candidate_id, responses[{critique_ref, stance: concede|defend|revise, note}],
                   revised_candidate? }                                 # phase 4
VerifierSignal   { candidate_id, runnable:bool, feasibility:0..1, log }  # phase 5
Score            { judge_vendor, candidate_id, novelty, soundness,
                   feasibility, clarity, rationale }                    # phase 6 (authorship hidden)
Recommendation   { ranked[candidate_id], verifier_weighted:bool, rationale }

Every record is persisted to the checkpoint store as it's produced; a crash resumes from the last completed phase.

2. Per-phase prompts click to expand

Phase 1 · Independent research — each peer, in parallel 
SYSTEM
You are an AI4SE research scientist. Survey ONLY the literature provided
below and identify ONE specific, underexplored gap in the given area.
Rules:
- Ground every claim in a provided reference id. Do NOT invent citations.
- Prefer a gap that could be tested with a small, runnable experiment.
Return JSON: ResearchBrief { landscape, gap, rationale, refs[] }.

USER
Area: {area}            Question (optional): {question}
Constraints: {constraints}
Retrieved papers (id · title · abstract):
{retrieved_papers}
Phase 2 · Propose — each peer turns its gap into an idea + minimal plan 
SYSTEM
Turn your identified gap into a concrete, testable research idea AND a
MINIMAL experiment plan runnable at toy scale to produce a first signal.
The experiment_plan MUST name, concretely:
  - dataset (small & publicly available; give name/source)
  - baseline(s) to compare against
  - the method / intervention
  - the metric and how it's computed
  - the SMALLEST end-to-end runnable step (what a 20-line script would do)
Return JSON: Candidate { title, gap, hypothesis, method, experiment_plan, refs[] }.

USER
Your research brief: {research_brief}
Phase 3 · Cross-critique — each peer critiques ALL candidates, authorship hidden 
SYSTEM
You are reviewing AI4SE research candidates (authorship anonymized).
Critique EACH candidate on novelty, soundness, and feasibility. Be
specific and adversarial but fair.
- If a claim is empirically checkable, set needs_verification=true
  instead of asserting it yourself.
- severity 1 (nit) .. 5 (fatal). Cite evidence_ref where possible.
Return JSON: Critique[] (one or more per candidate).

USER
Candidates (anonymized):
{candidates_without_vendor}

Blind critique of all three (incl. unknowingly one's own) is what lets us measure self-preference for RQ3.

Phase 4 · Rebut / revise — each author answers critiques of its candidate 
SYSTEM
Here are critiques of YOUR candidate. For each: concede, defend with
evidence, or revise. If revising, return the updated Candidate. Push any
empirically-checkable dispute to verification (don't argue it rhetorically).
Return JSON: Rebuttal { responses[], revised_candidate? }.

USER
Your candidate: {candidate}
Critiques targeting it: {critiques_for_candidate}
Phase 5 · Verify — verifier tool, not a peer 
# Increment 1 (mock): an independent model rates feasibility.
SYSTEM  Given an experiment_plan, estimate whether a competent engineer
        could implement & run a toy version in < 1 hour. Return
        VerifierSignal { runnable:bool, feasibility:0..1, log }.

# Increment 2 (real): generate → execute.
1. codegen agent emits a minimal runnable scaffold from experiment_plan
   (load toy data → run baseline+method on a few samples → print metric)
2. run in sandbox: container, no network, time/mem capped
3. runnable = exited 0 AND emitted the declared metric
   feasibility = f(runnable, #deps resolved, #auto-fixes needed)
Phase 6 · Judge / score — each peer scores all candidates, authorship hidden 
SYSTEM
Score each candidate (authorship anonymized) 1..5 on novelty, soundness,
feasibility, clarity. Your feasibility score MUST be consistent with the
verifier signal provided for that candidate (the signal outranks opinion).
Return JSON: Score[] with a one-line rationale each.

USER
Candidates (anonymized): {candidates}
Verifier signals: {verifier_signals}

# Aggregation (code, not LLM):
#   composite = w_n·novelty + w_s·soundness + w_f·feasibility + w_c·clarity
#   feasibility term clamped to verifier signal; mean across the 3 judges
#   → Recommendation.ranked ; human confirms / re-runs.

3. Termination & config

Loop phases 3→6 until (a) no critique of severity ≥ 3 is raised in a full round (consensus), or (b) n_rounds reached. Then judge + human confirm.

# config/ideation.yaml
stage: ideation
n_rounds: 2
seats:   { openai: gpt-5, claude: claude-opus-4-8, gemini: gemini-2.5-pro }
retrieval: { tools: [wiki, openalex, arxiv], k: 25 }   # tools selectable per round
verifier:  { mode: mock }          # increment 1 → { mode: sandbox } in increment 2
weights:   { novelty: .35, soundness: .25, feasibility: .25, clarity: .15 }
budget:    { usd_max: 5.0 }

Toy illustration of the run shape, not real output. The transcript is the eval datum: every brief, critique, rebuttal, verifier log, and score is on disk.

5. How this slice is the experiment harness

  • Swapping seats to all-one-vendor gives baseline B3; a single seat + self-debate gives B1; n_rounds: 0 single seat gives B0.
  • verifier.mode: mock vs real, and the candidate-with-vs-without verifier in judging, gives B4 (RQ2).
  • An anonymize: false flag in phases 3/6 gives B5 and the self-preference measurement (RQ3).
  • So every baseline is a config of the same code path — no separate harnesses to build or keep in sync.
