Open Questions Resolved (Q1–Q4)

Updated 2026-06-04 · All four resolved · Q3 = Hybrid/OpenAlex · Q4 = Checkpointed CLI

Resolving the four open design questions from Architecture & Design before any code. Two are decided; two are presented as options — click the tabs to compare.

Q1 · Model per vendor seat decided: ask each run

The panel is 3 symmetric peers, one per vendor (peers, not fixed roles — each proposes and critiques; judging is a panel vote + human confirm). No hard-coded default model. At the start of a debate the CLI prompts for which model fills each vendor seat and which retrieval tools the council may use this round (see Knowledge Layer), last-used offered as default, overridable by flags/config for repeatable runs.

$ council debate ideate --topic "..."
  OpenAI seat  [gpt-5]:            ▸
  Claude seat  [claude-opus-4-8]: ▸
  Gemini seat  [gemini-2.5-pro]:  ▸
  Retrieval tools  [x] wiki [x] openalex [x] arxiv [ ] semanticscholar
                   [ ] github [ ] paperswithcode [ ] web        ▸
# or non-interactive:
$ council debate ideate --topic "..." \
    --seats openai=gpt-5,claude=opus-4-8,gemini=2.5-pro \
    --tools wiki,openalex,arxiv

Q2 · Panel size & structure decided: 3 symmetric peers

v0 runs 3 symmetric peer agents, one model per vendor (OpenAI, Claude, Gemini). Every peer researches independently, proposes, and critiques the other two; the judge is an anonymized panel vote that the human confirms. Clean symmetry, lowest cost, and the cleanest experimental contrast (heterogeneous-3 vs. homogeneous-3 of one vendor). Larger / repeated panels are a later knob.

Q3 · Retrieval backbone decided: LLM Wiki + OpenAlex hybrid

Evolved 2026-06-04

The pluggable-interface principle below still holds, but the chosen composition is now a curated LLM-maintained wiki (synthesis) + OpenAlex (discovery) — see the dedicated Knowledge Layer page. The options below are the original framing, kept for rationale.

Principle

Mirror the LLM provider design: define a thin RetrievalProvider interface and never bind the core to a vendor. The only decision is which reference adapter ships first. All options below implement the same interface, so switching later is one adapter.

class RetrievalProvider(Protocol):
    async def search(self, query: str, k: int) -> list[Paper]
    async def get(self, id: str) -> Paper          # title, abstract, refs, year
# Paper carries enough to ground a claim: id, title, abstract, venue, year, url

A · Local corpus + embeddings offline

You drop in PDFs / BibTeX. We parse, chunk, embed (pluggable embedder), and index in a local vector store (e.g. sqlite-vec / FAISS / Chroma). Debate runs over your index. Zero external services.

No lock-in, fully private & reproducible
You must supply the corpus
Works offline; deterministic
Coverage limited to what you ingest

B · Open scholarly API broad coverage

Adapter over an open, free source — OpenAlex (CC0 data, no API key), arXiv, or Crossref. These are open datasets/APIs, not proprietary products like Elicit/Undermind. Swappable behind the same interface.

Broad, current coverage; no corpus prep
Network dependency + rate limits
Free, no account/lock-in (OpenAlex)
Less reproducible (index drifts over time)

C · Hybrid recommended default

Discover candidates via the open API (OpenAlex), cache + embed locally, then debate over the local index. You get coverage when online and reproducibility once cached — and either half degrades gracefully to option A or B.

Coverage of B + reproducibility of A
Slightly more moving parts
Cached corpus snapshot per project = citable
Two code paths to maintain

All three share one interface. Recommendation: ship A + B adapters, wire C as the default composition. Default open source = OpenAlex (no key, CC0).

Q4 · Execution model decided: Checkpointed CLI

This is how a debate run executes and survives. Debates are long and cost real money (many provider calls), so losing progress to a flaky API or Ctrl-C matters. The enabling design: keep the orchestrator a pure async generator that yields round results; a separate runner decides whether to stream, persist, or queue. That keeps all four options below a runner swap, not a rewrite.

1 · Synchronous CLI simplest

One process runs all rounds, streams to terminal, writes the transcript at the end.

Trivial to build & debug
Crash / Ctrl-C loses the whole run
Great for the first slice
No pause/resume; blocks the terminal

2 · Checkpointed / resumable CLI recommended for v0

Same single-process run, but each round's state is persisted as it completes. A crash or Ctrl-C resumes from the last checkpoint (council resume <run-id>).

Never lose an expensive debate
Need a small state schema + replay
Still simple; one process
No parallelism / background yet

3 · Job queue + worker platform-ready

Debates submitted as jobs to a queue (local task table + worker loop, or arq/RQ/Celery). Background runs, parallelism, pause/resume, and a future web UI plug in here.

Run many debates in parallel / background
Infra overhead (worker, broker)
Natural home for a later UI
Overkill for a personal v0

4 · Durable workflow engine heaviest

Temporal-style engine or a DB-persisted state machine with full replay guarantees.

Strong reliability & replay guarantees
Heavy dependency; steep setup
Scales to production
Far beyond current need

Recommendation: Option 2 (checkpointed CLI) for v0 — minimal but resumable. Because the orchestrator is runner-agnostic, upgrading to Option 3 when a UI arrives is a runner swap, not an orchestrator rewrite (matches "personal tool first → platform later").
