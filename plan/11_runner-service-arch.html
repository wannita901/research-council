Runner & Service Architecture

Drafted 2026-06-05 · How we go from one-shot CLI → watchable, interactive, served

The core orchestrator is runner-agnostic: it already emits a typed Event per phase via an emit callback. So "watch the agents debate", a backend service, and a front-end are all just different runners over the same event stream — no core redesign.

1. Interactivity — chosen: watch + rich review gate

LevelWhatNeeds
L0 · Watchsee research→propose→critique→… stream livesurface emit (CLI print, or SSE)
L1 · Review gate ✓at each round's judge step: iterate (another round), amend (round + your feedback), conclude (end on ranking), or select (end + pick)a reviewer hook (CLI prompt / POST endpoint)
L2 · Interject (later)steer / veto mid-roundbidirectional WebSocket + in-loop hooks

Gate actions (editorial set): iterate — run another round (peers only) · amend [comment] — another round with your feedback injected as a human critique · conclude — end now, take the panel's ranking (no human pick) · select [id] — end now, you name the winner (defaults to rank-1). A no-human (autonomous) run uses an internal auto that defers to the termination policy. Loops are capped at SAFETY_MAX_ROUNDS.

How human feedback enters the debate

A comment at the gate becomes a high-severity "human critique" (critic_vendor="human", severity 4) injected into the next round — so it flows through the existing critique → rebut → verify → re-judge machinery. No separate mechanism, and it keeps the debate going (severity ≥ 3 defeats consensus-stop). Because this happens at round boundaries, SSE (stream out) + a POST action (feedback in) suffices — WebSocket is only needed for true mid-round L2 interjection.

2. Backend — FastAPI over the same core

FastAPI is the pick: async, Pydantic-native (reuses our existing models verbatim), first-class WebSocket + SSE, background tasks. It's plumbing, not the contribution — consistent with "no heavy framework in the core". v0 needs no Redis/Celery: a per-run asyncio.Queue is the event bus (emit pushes, the stream drains). This is the "checkpointed CLI → job/service" upgrade flagged in Decisions Q4.

POST /debates            {topic, config}  → {run_id}     # starts a background task
GET  /debates/{id}/stream  (SSE)                           # live Event stream (watch)
POST /debates/{id}/action  {action: iterate|amend|conclude|select, choice?, feedback?}
GET  /debates/{id}         → status + Recommendation
# run_debate(...) already takes emit= AND reviewer=; the service routes emit→queue
# and reviewer→a future resolved by POST /action. CLI routes them to stdout/stdin.
Implemented 2026-06-05 — research_council/service/app.py

FastAPI app with all four endpoints; per-run asyncio.Queue bus + reviewer-future, exactly as sketched. interactive:false runs autonomously (auto-proceed); true awaits POST /action at each round. Run it with mise run serve (uvicorn). Verified: real server boots, autonomous run streams to done over SSE, and the interactive review gate resolves over HTTP. 23 tests green (offline, stub peers). No Redis/Celery — in-process per v0.

3. Front-end (future)

A pure consumer of the event stream — fully decoupled. Our typed, stable Event schema is the contract; any UI (a plain web dashboard, or a visual/animated one like pixel-agents) subscribes and renders. Deferred until the backend stream is proven; pixel-agents is one rendering option to evaluate then, not a commitment.

4. mise's role clarified

Once served, mise launches infrastructure, not individual debates: mise run serve (backend), later mise run web (front-end), plus deps/test. Debates are triggered through the API (front-end / curl / thin client). council debate remains a dev / in-process convenience and the offline test path.

5. What stays unchanged

  • The orchestrator, contracts, anonymization, verifier, checkpoint — all reused as-is.
  • emit already exists; the service just routes it to a queue instead of stdout.
  • Every baseline is still a config of the same core (the service starts the same run_debate).
Decisions locked (2026-06-05)
