Phase 4 · Build Specs

Observability & Telemetry

Drafted 2026-06-04 · Local-first · No paid SaaS · The trace is also the eval data

One principle drives the whole plan: observability is local, free, and identical to our eval dataset. Every debate already emits a structured record of itself; observability is just making that record complete, queryable, and viewable — without sending anything off-disk or paying anyone.

Why this is nearly free

The checkpoint store (see Architecture §6 / Vertical Slice) already persists every phase event for resume. Observability reuses that exact stream — we add per-call telemetry + a cost governor + a viewer. The same JSONL that lets a crash resume is what we later load into pandas to compute RQ metrics. Build it once, use it twice.

Three pillars, mapped to local choices

PillarWhatHow (free, local)
LogsHuman-readable run progress, warnings, errorsPython logging, JSON formatter, correlation id = run_id
MetricsCost, tokens, latency; RQ metricsTelemetry records → pandas aggregates
TracesThe full debate timeline, phase by phaseAppend-only JSONL trace + an HTML run report

Tier 0 — default (zero external services)

1 · Run trace (the one artifact)

Append-only JSONL per run_id. Every phase output is an event with a shared envelope. This is the transcript, the checkpoint log, and the eval datum — one file, three jobs.

// runs/2026-06-04-ideation-a3f1/trace.jsonl
{ run_id, ts, phase, round, agent_vendor?, event_type, payload }
// event_type ∈ research_brief | candidate | critique | rebuttal
//            | verifier_signal | score | recommendation | human_action

2 · LLM call telemetry

One record per provider call — the basis for cost, latency, and reliability views. (We compute cost in the shared provider helper from a small per-model token-price table.)

{ run_id, phase, agent_vendor, provider, model,
  prompt_tokens, completion_tokens, cached_tokens,
  cost_usd, latency_ms, retries, error? }

3 · Cost / budget governor

  • Running USD total per debate; enforce budget.usd_max — on breach, abort gracefully and checkpoint (never a surprise bill).
  • Per-phase and per-vendor cost breakdown in the run summary.
  • Prompt caching on shared context (corpus, rubric) across rounds to cut spend — tracked via cached_tokens.

4 · Structured logging

  • INFO: phase boundaries, decisions, final ranking. WARNING: retries, a degraded/dead vendor. DEBUG: full prompts + responses (behind a flag — verbose & may hold sensitive text).
  • Every line carries run_id so a single debate is greppable end to end.

5 · Derived metrics = RQ metrics

Computed from the trace by one script — observability and evaluation share the same pipeline:

  • rounds_to_converge, critique counts by axis/severity
  • proposal_diversity (embedding distance among the 3 independent briefs/candidates) — evidence heterogeneity produces diverse starts
  • self_preference_rate (own-candidate score vs others, anonymized vs de-anonymized) — this is RQ3
  • verifier pass rate, feasibility distribution — this is RQ2

6 · Run report (HTML, offline)

Generate runs/<id>/report.html reusing this plan's CSS: the phase timeline, candidates, critiques, costs, and final ranking — openable in a browser, no server. It also seeds the future UI, which would stream the very same events live.

Tier 1 — optional, free OSS, self-hosted

Only if Tier 0's JSONL + report proves insufficient for debugging multi-agent flows:

  • Arize Phoenix or Langfuse — both free OSS, self-hostable via Docker, no SaaS bill. They give span/trace UIs and dashboards over LLM calls. Bridge via OpenTelemetry instrumentation; off by default, opt-in env flag.
  • Cost: adds one local container. Worth it only when visual trace debugging pays for itself.
Explicitly NOT used (paid / data leaves disk)

No LangSmith, AgentOps, or hosted Weights & Biases. They're convenient but send debate content to a third party and/or meter you. Everything here stays local; the optional Tier-1 tools are the self-hosted OSS editions only.
