Phase 4 · Build Specs

Knowledge Layer — LLM Wiki + OpenAlex

Drafted 2026-06-04 · Retrieval = curated wiki (always) + per-round selectable discovery tools

Retrieval is a registry of RetrievalProvider sources selected per round: always the curated, LLM-maintained wiki (deep synthesis that compounds), plus the discovery tools you enable for that debate (OpenAlex, arXiv, Semantic Scholar, GitHub, …). The wiki design follows Andrej Karpathy's LLM Wiki pattern (explainer).

Why a wiki, not just RAG

Gap-finding (our Phase 1) is synthesis across documents — and the wiki's lint pass already surfaces "contradictions, stale claims, and gaps." The wiki's core maintenance operation is a primitive of the research task itself. It excels on a bounded curated corpus (100–500 sources); OpenAlex covers the "massive & fresh" case where RAG-style discovery still wins. Using both plays each to its strength.

2. Write side vs read side key split

Write side — automated ops

Ingest (drop a source → a librarian agent updates 10–15 pages, cross-links, flags) and lint (find contradictions, stale claims, orphans, gaps) run as platform ops — council ingest / council lint — with the guardrails in §5. Offline/async; not in the debate hot path.

Read side — the platform

WikiProvider.search/query navigates index.md, pulls relevant pages, and returns synthesized notes with citations back to raw/. Debates read a committed snapshot.

Decision (revised 2026-06-04): ingest/lint are automated from the start as platform ops, with the guardrails in §5 — not a manual Claude Code workflow. The maintainer agent, taxonomy, and routing rules are specified in Wiki Librarian Design.

3. The hybrid read path

HybridRetrieval.search(topic, tools):      # `tools` = the set enabled this round
  1. always: WikiProvider.query(topic)         # curated, synthesized memory
  2. fan out to each enabled discovery tool, in parallel:
       openalex · arxiv · semanticscholar · github · paperswithcode · web
  3. dedup by DOI/title · queue new externals for ingestion  # wiki compounds
  return notes[]  with a provenance tag = the source each came from

The enabled tools set is chosen at round setup (see below) and recorded in the run trace; every returned item is provenance-tagged so a peer (and our logs) always know which source a claim came from.

All sources implement the same RetrievalProvider interface and are registered by name. At debate setup — the same step that asks which model fills each vendor seat — the CLI also asks which retrieval tools the council may use this round, so capability and cost are controlled per debate.

Eval discipline

The enabled tool-set is an explicit experimental variable: fixed across all conditions in an experiment batch and recorded in every run trace (next to the seats + wiki commit hash). web is off during eval. "Does richer retrieval help debate?" can later be studied deliberately by varying this set.

MCP — optional, later (decided 2026-06-05)

Tools connect via direct adapters today. MCP (Model Context Protocol) is recorded as a future optional implementation behind the same RetrievalProvider — an MCPRetrieval adapter that wraps an MCP server as just another selectable tool (dedup/provenance unchanged). Direct adapters stay the default because the controlled eval needs pinned, reproducible retrieval and third-party MCP servers drift. Letting peers call tools agentically via MCP is a separate future mode (non-deterministic → complicates the controlled comparison), not a drop-in. Exposing research-council itself as an MCP server is a future interop play.

4. Reproducibility & bias controls eval-critical

The wiki is a mutable, LLM-generated artifact — handle with care
  • Snapshot per run: the wiki is a git repo; record the commit hash in every run trace so any result is tied to an exact knowledge state.
  • wiki-on vs wiki-off becomes an explicit eval condition (added to Research Framing's ablations) — isolates the wiki's contribution and guards against it doing the work we attribute to debate.
  • Novelty grounded externally: novelty is judged against the external literature, never the wiki's own synthesis — otherwise the system could echo itself and distort novelty scores.
  • Contamination timeline: log.md date-stamps every ingest, so we can reason about what was "known" when, alongside model cutoffs.

5. Automating ingest/lint — what to consider new decision

Automating the write side is the right call (the wiki maintains itself and compounds), but it shifts real responsibility onto the platform. The considerations, with my recommended defaults:

ConsiderationWhy it matters · default
Librarian modelMaintain the wiki with one fixed, cheaper model (consistent structure/style), not the debate panel. Keeps the wiki vendor-neutral; avoids cross-vendor drift.
Snapshot isolationDebates read while ingest writes. Writes stage on a git branch → validate → merge; debates always read the last committed snapshot. No torn reads.
Quality gate vs "wiki rot"Auto-edits can hallucinate or corrupt pages. Gate each ingest with schema validation + a lint pass; optional human-review (PR-style) before merge; git makes every change revertible.
Dedup / idempotencyRe-ingesting the same/similar source must merge, not duplicate. Hash sources; detect near-duplicates before creating pages.
Transactional writesA partial ingest must never leave the wiki inconsistent: stage → validate → commit, else roll back.
Prompt-injection safetyExternal PDFs/web are untrusted — a paper can hide instructions. Sanitize; the ingest agent treats source text as data and never executes tool calls from it.
CostEach source touches 10–15 pages = many calls. Cheaper librarian model + batching + budget caps; ingest is offline so it never inflates per-debate cost.
The one that can break the paper — self-contamination

If a debate's own discoveries/ideas get auto-ingested, the system can start citing its own generated content as if it were external literature — silently inflating novelty. Hard rule: two separate namespaces — raw/external/ (real sources, the only thing that counts as prior art) and raw/internal/ (system-generated notes). Novelty is judged against external/ only.

7. Scope for v0

  • Build (read): WikiProvider, OpenAlexProvider, HybridRetrieval behind the Protocol.
  • Build (write): council ingest / council lint via a fixed librarian model; git stage→validate→merge; external/ vs internal/ namespaces.
  • Seed: ingest a small AI4SE corpus to test against.
  • Record: wiki commit hash in the run trace from day one.
  • Defer: human-review UI for merges; reranking; full-text PDF RAG.
