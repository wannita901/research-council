Phase 7 · Implementation (v2)

Conversational Conductor — council run

Built 2026-06-09 · one command drives the whole lifecycle, gated by conversation · 111 tests green

Until now the lifecycle was one CLI command per stage (project new → approve → approve). The user asked: can a facilitator run the council so I just talk to it, not type commands? Answer: a conductor — council run — that walks onboarding → ideation → experimentation → writing and pauses at each boundary to ask you (go / redo / stop) instead of making you issue a command. The human gates stay; they just become questions.

1 · The flow

$ council run --live
facilitator: what's your research question?        ← onboarding (clarifying Qs, live)
[Stage A ideation]  (its own per-round gate refines the idea when interactive)
gate · ideation     selected: ""
  Run experiments on this idea?  [▶ run experiments / ↻ redo ideation / ✗ stop]
[Stage B loop]      feasible f1=0.62 · 2/2 approved
gate · experimentation
  Write up the paper?  [▶ write the paper / ↻ re-run experiment / ✗ stop]
[Stage C loop]      accepted · mean 0.74 · paper.pdf
gate · writing
  Finish the project?  [✓ finish / ↻ re-run writing / ✗ stop]
project complete 🎉

2 · Design decisions

DecisionChoice
Surfaceterminal REPL first (chosen over backend+SSE). Smallest path to "just talk to it"; the conductor logic is the shared core the FastAPI backend + web UI (17) will later sit on.
Reuse, don't duplicatewraps the existing pieces — facilitator onboarding, run_ideation + its _cli_reviewer round-gate, the Stage B/C loop engines (18), _venue_choice, and the lifecycle state machine / ProjectStore.
Gates preservedthe human gate between stages is kept — rendered as a question. go → approve_and_advance; redo → re-run that stage's engine on its input handoff (build_handoff); stop → save & exit.
Resumablestate is persisted each step; a paused run continues with council project approve <id> (or another council run would start fresh). Per-stage CLI remains the power/automation path.
Non-TTY = scriptableoff a TTY the gates auto-proceed ('go') and stages fall back to stubs — the whole pipeline runs headless in one command (this is the offline test).
Live vs offline--live runs real engines (keys; Docker for B); offline uses stub peers + stub stages. --profile bounds the B/C loops; --venue optional (else council recommends + you confirm).
