Phase 7 · Implementation (v2)

Can it actually generate a paper with verifiable artifacts?

Audit 2026-06-14 · grounded in the 3 live projects on disk + a code read of debate/writing.py, debate/experimentation.py, verify/*, agents/writer.py

The pipeline runs end-to-end and emits the right files (proposal → results.csv + per-RQ code/figures → paper.md/.tex/.pdf). But "verifiable" means a reader can check that the paper's claims follow from the artifacts, and that the artifacts can be re-run. On both counts the chain is currently open: numbers in the prose are never checked against the data, experiments carry no reproduction manifest, citations are filtered but not resolved, and the council's own approval signal is ignored at the Stage B→C boundary.

Headline promise vs. reality
The README states two principles: "every claim must cite a source or show experiment evidence" and "nothing advances without your approval." The first is enforced for citations (keys not in the wiki allow-list are dropped) but not for numeric claims. The second holds for human gates but not for the council's approval — see Gap 4.

The smoking gun — an unbacked numeric claim (project …103845)

experiment/results.csv contains exactly three metrics: signed_NxT_interaction=0.000137, interaction_effect_size=0.3900, interaction_F=5.0812. The Results section correctly cites all three (F=5.08, η²=0.39, 1.37×10⁻⁴). But it then adds:

"Tool-call efficiency decreases monotonically with N, falling from a mean of 0.81 at N=2 to 0.57 at N=16 … First-error step index decreases as N increases…"

Neither 0.81, 0.57, "first-error step index", nor "post-error recovery rate" appears anywhere in results.csv or the RQ logs. They are plausible, on-topic, and unverifiable — exactly the failure mode the product claims to prevent.

3 · Prioritised gaps & recommended fixes

#GapRecommended fixEffortImpact
1 Numeric claims are never checked against the data. Prose can state any number; nothing fails. Add a verify/claims.py claim-checker: extract numeric tokens + their metric labels from the draft, fuzzy-match against results.csv (+ RQ logs) within tolerance, and emit a paper/claims.json evidence map (claim → row / UNBACKED). Feed every UNBACKED claim back into the PC review loop as a blocking change-request so the writer must cite or delete it. M High
2 Citations filtered, not verified. Wiki-only allow-list; ungrounded refs merely tagged "needs verification"; no resolvable bibliography. Resolve each allowed citation to a real identifier via the already-present retrieval/{semanticscholar,openalex,arxiv}.py providers; emit paper/references.bib with DOIs/arXiv ids; drop or hard-flag anything unresolvable. Closes the "cite a source" half of the promise with a checkable artifact. M High
3 Experiments aren't reproducible. No seed, no pinned versions, no code hash, no re-run command. Per RQ, write a repro.json (random seed, resolved pip freeze, sha256 of experiment.py, sandbox image digest, the exact run command, captured METRIC value) + a top-level reproduce.sh that re-runs all RQs and diffs metrics against the recorded values. M High
4 Writing proceeds on unapproved experiments. All RQs approved=False → full paper still drafted as if it were a result. Gate the B→C handoff on the council's own signal: if no RQ is approved, either block writing (require human override) or force the paper into an explicit "negative/feasibility result" template so it can't overclaim. Surface approved-RQ count in project status. S High
5 PDF compile is unreliable (0–1 of 3 runs). build.log shows a path-resolution failure invoking latexmk. Run the TeX engine with an absolute --cd into paper/; treat a missing PDF as a Stage-C failure surfaced in project status (not a silent skip). Add an offline smoke test that compiles a fixture .tex so the path bug can't regress. S Med
6 Single-observation statistics. n=1 per cell; an F-test reported with df=0. The paper itself admits the stats are descriptive. Have the coder emit replicate runs (seeds) and report mean ± CI; the claim-checker (Gap 1) then verifies the reported CI exists in the data. Lower priority — correctness of the science, not of the artifact chain. L Med
Recommended first slice (next iteration)
Gap 1 — the claims-to-evidence checker. It is the single change that turns "a paper that mentions numbers" into "a paper whose numbers are verifiable", it directly delivers the named artifact (claims.json), it is offline-testable with the existing results.csv fixtures (no API keys, per the dev-verification preference), and it composes with the existing PC-review loop rather than adding new machinery. Gap 4 (the approval gate) is a tiny, high-value companion.

4 · What already works (don't rebuild)

  • Real experiment code is saved and re-runnable in principle (experiment/<rq>/experiment.py + requirements.txt).
  • Figures are real plots of computed data, collected from the sandbox and embedded in the paper (plan/24).
  • Citation invention is already blocked by the allow-list filter — we only need to add *resolution* on top.
  • The METRIC name=value convention + results.csv give the claim-checker (Gap 1) a clean target to match against — the data half of the contract exists; only the *check* is missing.

5 · Decided vs open

Decided (this audit)
The gap is verification, not generation. Sequence the fixes claims-checker → approval-gate → repro-manifest → bib-resolution → latex-robustness. Why: claims-checking is the highest impact, offline-testable, and reuses the existing review loop.
Open
Tolerance + label-matching strategy for the claim-checker (exact vs. rounded vs. unit-aware), and whether an UNBACKED claim is blocking or merely flagged in v1. Resolve when building Gap 1.
